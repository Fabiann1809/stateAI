# Decision log

Decisions not fully specified by `SPEC.md`, recorded so they can be reviewed later. Newest last.

| # | Decision | Reason |
|---|---|---|
| 1 | The domain uses 3 activation levels (`LOW`, `MEDIUM`, `HIGH`) plus a restlessness flag. | Health Services exposes no RR intervals (see `sensors.md`). |
| 2 | UI names for the levels: **Enfocado** (`LOW`), **Normal** (`MEDIUM`), **Sobrecarga** (`HIGH`). | Chosen by the product owner. Screens and docs still describe them as estimates. |
| 3 | Default target block per category is the midpoint of the spec range: deep work 75, study 40, reading 40, collaborative 45, other 45 min. | Values are configurable constants and are learned per activity anyway. |
| 4 | Manual dependency injection through an `AppContainer`, no Hilt. | Less build overhead and easier to read. |
| 5 | Category "sensitivity" in 6.3 is read as **detection sensitivity** (how readily thresholds react). The hourly vibration cap is a separate value: deep work 2, study 3, reading 2, collaborative 4, other 3. | The spec table does not define the cap; quieter caps protect the categories that need long, uninterrupted blocks. |
| 6 | Haptic policy rules (event type, rate limiting) live in `:core-domain`; `:haptics` only turns events into Android vibrations. | Keeps the rules testable on the JVM and the Android module thin. |
| 7 | When the target block is reached, the "suggested pause" pattern fires once. | 6.2 has no dedicated end-of-block pattern; a pause suggestion is what the event means. |
| 8 | Until Room persistence arrives, activities live in an in-memory repository behind the domain interface. | Lets the picker work now without building persistence ahead of its phase. |
| 9 | `minSdk` is 33 (Wear OS 4) instead of 30. | Wear OS 3 is outdated by 2026; API 31+ provides `VibratorManager`, and Wear OS 4 is where the Health Services sensor panel works for synthetic data. |
| 10 | The breathing guide is exempt from the vibration rate limits, like start events. Exempt events do not count toward the limits. | The guided pause is started by the user and pulses every few seconds; limiting it would break it. |
| 11 | `SensorSample` and the `SensorSource` interface live in `:core-domain`; `:sensors` holds the simulator and the Health Services adapter. | Same dependency rule as repositories: the domain owns the interfaces it consumes, so feature computation stays testable on the JVM. |
| 12 | A sample carries a nullable heart rate and the linear acceleration magnitude in m/s². | Health Services may skip seconds; linear acceleration removes gravity so "movement" is comparable across wrist positions. |
| 13 | Segments keep a per-window level trace (`L`/`M`/`H`/`-`), the minutes of app cues and calm/movement means. | Phase 5 learning (cycles, focus profile, baseline, energy) needs per-minute detail; it is a derived summary, not the raw signal. Room migrates the schema automatically. |
| 14 | Cycle detection uses a Schuster periodogram with a session-shift permutation test, removes session-locked effects, and requires split-half agreement. | Session start times repeat daily, so session-locked effects (like the end-of-block cue) would otherwise look like cycles. Details and results in `cycles.md`. |
| 15 | The baseline is refined with an EMA (alpha 0.2) of the heart rate in calm windows of each session. | "Calm in session" is the closest observable to resting without asking the user to sit still again. |
| 16 | An activity's learned block is the running mean of its valid session durations; its movement limit is 1.5 × its mean clean-window movement. Both blend with the category by `n/(n+5)`. | Simple, explainable, and converges with few sessions. |
| 17 | Feedback moves an activity's sensitivity by ±0.02 (bounded to ±0.2) only when it contradicts the estimate (bad after mostly focus, good after mostly load). | Feedback labels a whole segment, so it can only nudge global sensitivity. |
| 18 | Estimated energy: 0.10/0.12/0.30 points per minute at LOW/MEDIUM/HIGH, +0.10 when restless, +6 per pause that improved the state, ×0.8 / ×1.2 in learned good / bad hours. Low below 25. | Product choices that end a full mixed day around a quarter of the battery; documented as an indicator, not physiology. |
| 19 | The next-activity suggestion counts same weekday-and-hour segments double and same-hour segments once, and needs a score of 4. | Predicts routines from a few weeks without suggesting on thin evidence. |
| 20 | The ML evaluation trains on three synthetic users and tests on two held-out ones, against a Python port of the rules. The report states the actual results, which differ from the spec's expectation. | Results: rules 0.52 accuracy (0.72 with the true resting rate), logistic regression 0.85. The single 2-minute calibration can land on an engaged minute and bias every later window; see `ml-python/reports/classifier.md`. |
| 21 | `android.uniquePackageNames=false` in `gradle.properties`. | LiteRT 2.x ships `litert` and `litert-api` with the same namespace, which AGP 9 rejects by default; with the check off it only warns. Revisit when LiteRT fixes its packaging. |
| 22 | The classifier is chosen at build time (`-Pstateai.classifier=rules|model`); rules stay the default. | The model is a pipeline demonstration trained on synthetic data; the rules remain the reference behavior. |
| 23 | The model decides the level only when its top probability is at least 0.5; otherwise, or when it throws, returns non-finite values or fails to load, the rules decide. | With 3 levels chance is 1/3; 0.5 means the model clearly prefers one level. The rules are always computed anyway for restlessness. |
| 24 | The end-to-end simulation uses a closed-loop version of the synthetic user: each work minute adds effort (double when strained), each pause minute removes 8, and resuming redraws the mode. Days are four 90-minute periods; the fixed timer is 25/5. | The offline generator cannot react to pauses. The recovery rules decide how much pausing pays off, so results describe this simulated world only. |
